# 知识资产与记忆协议

本协议只管理用户明确要求沉淀或确认更新的内容。它不是自动记忆：只有实际读取了文件并完成写入后，才能说知识已保存。

## 四类资产

| 文件 | 作用 | 主键 |
|---|---|---|
| `knowledge/ideas.md` | 创意、推导、评分与当前状态 | `IA-YYYYMMDD-XX` |
| `knowledge/connections.md` | 跨概念机制、边界与置信度 | `CN-YYYYMMDD-XX` |
| `knowledge/preferences.md` | 原始反馈、偏好升级和撤销 | `FB-YYYYMMDD-XX`、`PREF-YYYYMMDD-XX` |
| `knowledge/evolution.md` | 方法论变更、确认状态与版本 | `EV-x.y.z` |

测试样例、临时推断和未获授权的候选不进入这些文件。测试结果保存在 `tests/`，不能当作真实用户历史。

## 记录格式

每条记录以二级标题开始，标题包含稳定 ID，随后使用统一字段：

```markdown
## IA-YYYYMMDD-XX — 创意名称

- **日期**：YYYY-MM-DD
- **主题**：主题
- **创意名称**：名称
- **核心构想**：机制、对象和结果
- **来源**：来源与信息层级
- **推导逻辑**：从线索到方案的可审查推导
- **评分**：N/R/V/F/E、加权分、置信度和警告
- **当前状态**：待验证 / 实验中 / 采用 / 暂缓 / 放弃
- **去重键**：稳定、短小、由问题机制形成的键
- **合并记录**：无，或关联的重复/近似记录
```

### 创意字段

必填：

- 日期。
- 主题。
- 创意名称。
- 核心构想。
- 来源。
- 推导逻辑。
- 评分。
- 当前状态。
- 去重键。

建议额外保留：

- 合并记录。
- 最近更新时间。
- 实验或反馈 ID。

### 关联字段

必填：

- 日期。
- 概念 A。
- 概念 B。
- 共同原理。
- 关联类型。
- 应用场景。
- 适用边界。
- 置信度。
- 去重键。

同一去重键只能有一条活动记录。概念顺序规范化后相同的记录也视为同一关联。

### 反馈字段

反馈记录存放在 `preferences.md` 的“反馈事件”区，必填：

- 日期。
- 关联创意；不适用时写“不适用”。
- 原始反馈。保留用户原话或可核实行为，不改写成更强结论。
- 偏好级别：明确偏好 / 待确认模式 / 单次信号。
- 授权状态：已授权 / 未授权。
- 状态变更。
- 重复检查。

反馈 ID 一经创建不重新编号。后续反馈追加为新的 `FB` 记录，并引用先前记录。

### 偏好字段

只有满足以下条件的偏好才能建立活动 `PREF`：

- 用户明确表达喜欢、不喜欢或以后如何处理。
- 有至少一条真实 `FB` 记录作为依据。
- 用户已授权记录。
- 内容没有与核心安全或事实边界冲突。

活动偏好必填：

- 日期。
- 偏好类型：明确偏好。
- 内容。
- 反馈依据。
- 确认状态：已确认。
- 当前状态：有效。

撤销偏好时保留原记录，将当前状态改为“已撤销”，并创建新反馈或新偏好记录说明替换关系。

## 写入事务

1. **确认授权**：用户明确要求保存、更新、合并或升级。探索请求本身不等于授权。
2. **读取目标**：读取目标文件及其关联的创意、反馈和版本记录。
3. **检查重复**：运行 ID、去重键、标题和机制级检查。
4. **准备最小变更**：只追加或修改当前任务需要的内容。
5. **保留旧内容**：不覆盖历史；变化通过状态、替代表或追加事件表达。
6. **建立引用**：反馈引用创意，偏好引用反馈，版本引用用户确认。
7. **验证**：检查重复 ID、缺失字段、断裂引用和未确认升级。
8. **报告结果**：列出实际更改、未写入内容和需要用户确认的事项。

无法写入时，输出完整的可合并 Markdown 片段，并标记“尚未保存”。

## 反馈升级

| 信号 | 可记录内容 | 不可推断 |
|---|---|---|
| 单次喜欢 | 原始反馈、相关创意状态 | 稳定审美偏好、以后都采用同类方案 |
| 单次拒绝 | 原始反馈、相关创意状态 | 永久排除整个领域 |
| 多次相似选择 | 待确认模式、样本数、缺失证据 | 未经确认的正式偏好 |
| 用户明确声明 | 可建立已确认偏好 | 将声明扩展到未说过的领域 |
| 实验支持 | 状态与结果记录 | 把单个实验当成普遍规律 |

### 状态变更

- `待验证 → 实验中`：需要用户采纳、实际实验启动或明确指令。
- `实验中 → 采用/放弃`：需要结果或明确决定。
- `暂缓 → 待验证`：需要条件变化或用户重新激活。
- 不因一次“听起来不错”直接改为“采用”。

状态变化与反馈写入同一事务，但反馈原文和状态是两类事实，不能混写。

## 重复检测

去重从强到弱分四层：

### 1. 精确身份

ID 相同必须拒绝新增，改为修正原记录或建立版本。ID 不能因内容小幅变化而改变。

### 2. 去重键

创意去重键和关联去重键必须稳定。精确去重键相同视为同一记录：

- 新表达是更清楚的名称：可追加别名。
- 新内容补充边界或证据：更新原记录并标记更新时间。
- 核心机制变化：建立新记录，引用原记录为前身。
- 无法判断：保留为待确认候选，不自动合并。

### 3. 标题与结构近似

名称规范化后相同，通常视为重复。名称高度相似且目标问题、核心机制、使用场景一致时，视为近重复。

仅有相似名称但机制不同，可以作为新记录，并在“合并记录”中说明区别。

### 4. 语义判断

逐项比较：

1. 目标问题是否相同。
2. 核心机制是否相同。
3. 目标用户与场景是否相同。
4. 价值来源或资源模型是否相同。
5. 是否只是更换名称、比喻或界面。

前两项相同通常足以合并；只有名称相似不足以合并。脚本或标题相似度只能发出警告，最终语义判断必须说明依据。

## 冲突处理

- **事实冲突**：保留各自来源和日期，标记“待核实”，不选边写入为确定事实。
- **偏好冲突**：保留旧偏好，标记为“已撤销”或“待确认”；新增反馈说明变化原因。
- **状态冲突**：采用有日期和依据的最新事件，同时保留状态历史。
- **版本冲突**：核心规则以用户最后明确确认的版本为准；其他建议保持“待确认”。
- **引用断裂**：不删除记录，先补引用或标记缺失，再决定是否合并。

不得静默覆盖。无法安全拆分时停止自动更新，请用户选择。

## 版本迭代

### 版本号

采用语义化版本：

- **Patch**：措辞、示例或记录格式中的兼容修正。
- **Minor**：新增模式、模板、知识字段或验证能力。
- **Major**：改变核心方法、评分权重、默认权限或事实边界。

Phase 3 的知识协议和验证能力属于 minor 变更，因此记录为 `0.3.0`。

### 版本记录

每个 `EV` 记录包含：

- 版本号。
- 日期。
- 原有问题。
- 优化建议。
- 具体修改。
- 预期收益。
- 用户确认状态。
- 应用状态。
- 实际修改。

状态只使用：

- `待确认`：建议已形成，但不影响正式规则。
- `已应用`：用户已确认且修改已完成。
- `已回滚`：保留变更与回滚日期，不删除历史。

“已应用”必须包含可核对的确认或用户直接发起的开发任务。不能把测试中的模拟确认写成真实用户批准。

## 阶段复盘

- 只有真实有效探索和反馈记录可以进入统计。
- 达到十次有效探索后可生成阶段报告；不足时明确样本数。
- 认可率必须有明确分母。
- 重复率按检测层级分别报告。
- 偏好趋势区分明确偏好、待确认模式和单次信号。
- 优化建议与已应用版本分栏，不把建议写成事实。

## 验证与报告

可使用：

```text
python scripts/validate.py <knowledge-directory>
```

验证器只读，检查：

- 必需文件和字段。
- 重复 ID、标题与去重键。
- 反馈引用的创意是否存在。
- 偏好是否有真实反馈依据和确认。
- 版本是否重复，已应用版本是否存在确认。

最终报告必须区分：

- 实际新增。
- 实际更新。
- 合并或拒绝重复。
- 保持待确认。
- 未写入。
