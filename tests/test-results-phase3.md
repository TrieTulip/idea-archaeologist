**结论**：反馈升级和授权门禁均按协议工作。

## TEST P3-03：重复检测与合并

### 负向重复夹具

`duplicate/` 包含两个不同 ID 的创意，二者使用相同的去重键 `decision-evidence-map`，目标问题和核心机制相同。

实际结果：

```text

```

验证器以非零状态退出，并同时指出两个冲突记录，没有静默选择其中一条。

### 正向合并

新候选“决策证据导航”与“决策证据地图”具有同一目标问题、机制和去重键。更新事务没有创建第三条创意，而是在原记录的“合并记录”中说明：

> 已合并且不新增“决策证据导航”，因为目标问题、机制和去重键相同。

执行检查：

- 更新前后创意数均为 2。
- 没有出现新的 IA 标题。
- 旧创意 ID 保持稳定。
- 既有来源和推导保留。
- 合并依据写在原记录中，可追溯。

### 边界

标题相似度只是警告，不是自动合并依据。不同机制、场景或价值来源的近似名称仍需模型或用户审查。

## 实施中发现并修复的问题

首轮验证失败，原因是近似标题检查把 `Record` 对象传给只接受 ID 的 `record_kind` 函数，触发 `AttributeError`。

修复后：

- 正式空库通过。
- base 历史夹具通过。
- after 更新夹具通过。
- duplicate 和 unauthorized 负向夹具按预期失败。

该发现说明此次验证确实执行了带记录的历史路径，而不只是检查空目录。

## 当前限制

- 这是协议自检，不是独立用户行为验证。
- 去重键和语义机制仍需生成方或用户审查；验证器只能检查结构、精确键和标题近似。
- 正式知识库没有真实用户创意和反馈，因此无法生成有效阶段趋势。
- 下一阶段的长期统计应以真实记录为基础，不能复用测试夹具。
